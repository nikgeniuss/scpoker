# Архитектура и подсказки POKER HUB

> Технический контекст проекта. Читается, когда задача касается архитектуры — не каждую сессию.
>
> Ранее эти разделы жили в `CLAUDE.md §3`, `§4`, `§8.2`, `§8.3`. Вынесены 2026-05-29 в рамках декомпозиции.

## Стек

- **client/** — React 19 + Vite + Tailwind v4 + Zustand + Framer Motion + react-router-dom + react-hot-toast + zod + lucide-react + socket.io-client + `@twa-dev/sdk` (Telegram Mini App)
- **server/** — Node + Express 5 + Socket.IO + bcrypt + jsonwebtoken + nanoid + uuid + dotenv; хранилище — JSON-файлы в `server/data/`
- **shared/index.ts** — общие типы (`Card`, `Player`, `GameState`, `SOCKET_EVENTS`)
- Запуск всего: `npm run dev` из корня (поднимает клиент и сервер параллельно через `concurrently`)

Серверные пути импортов используют `.js` в конце даже для `.ts` (ESM + NodeNext) — это норма, не «ошибка опечатки», не править.

## Особенности (не трогать без задачи)

- В `server/src/game/*.ts` типы `Card`, `Player`, `GameState` (и `RoomInfo`, `CreateRoomOptions`, `RoomStatus`, `JoinDeniedReason`, `SOCKET_EVENTS` и др.) продублированы локально вместо импорта из `shared/`. Это из-за `rootDir: "./src"` в [server/tsconfig.json](../server/tsconfig.json) — shared лежит вне rootDir. Не «чинить» фоном — попытка через tsx+NodeNext+path mapping уже была и не сработала (см. «Грабли» ниже). Каждое новое поле в shared надо синхронизировать вручную в server-локальных типах.
- `JWT_SECRET` и `ALLOWED_ORIGINS` берутся из [server/src/config.ts](../server/src/config.ts) (он же грузит .env первым делом). В dev — fallback с warning; в `NODE_ENV=production` без них `process.exit(1)`. Хочешь прод — задать в .env.
- В dev CORS открыт `origin: '*'` (через config). В проде — whitelist из `ALLOWED_ORIGINS` (запятые-список) с `credentials: true`.
- Хранилище — JSON-файлы в `server/data/`: `users.json`, `design.json`, `settings.json`, `rooms.json` (снапшот метаданных комнат). Активные раздачи (deck/pot/ставки/карты/фаза/waitlist) с 2026-06-18 переживают рестарт: снапшот пишется в `active-hands.json` ([activeHandPersistence.ts](../server/src/game/activeHandPersistence.ts)), применяется в `gameManager.restoreActiveHands()` из [index.ts](../server/src/index.ts). Метаданные комнат — из `rooms.json`.

## Подсказки по проекту

### Состояние переключателей рума (снимок 2026-09-09)

> `server/data/` в `.gitignore` — фактические настройки живого рума в репозиторий не попадают, поэтому фиксируем их здесь. Всё меняется в админке; при расхождении источник правды — файлы в `server/data/`.

**Включено:** рейк рума 1.5% / cap 3 BB (`settings.json` → `defaultRake`, применён ко всем столам, включая ботовые); депозитный бонус (HUB, первый 2% / релоуд 0.5%, потолок 2000, от 5 USDT, отыгрыш 3×, 30 дней); рейкбэк (Bronze 10% → Diamond 50%, окно 30 дней); визит-бонус/стрик; достижения; миссии недели; сундуки; гонки лидеров (500/300/150 HUB, неделя); рефералка (100/30 HUB + 5% с рейка); магазин лояльности; косметика; Bad Beat Jackpot; приём платежей (`payments.enabled=true`).

**Выключено осознанно (решение пользователя 2026-09-09):** Rabbit Hunting (`paidFeatures.rabbitHunt`) и платный режим HUD (`paidFeatures.hudMode` = `free`) — «на старте лучше давать больше, чем брать».

**Платежи:** сети тестовые (`TRON_NETWORK=shasta`, `EVM_NETWORK=testnet` в `server/.env`), секреты лежат там же с июня. Фактически активен ТОЛЬКО адаптер `ethereum`: сеть включается лишь при заданном контракте USDT, а прописан один `ETH_USDT_CONTRACT`. Для Tron/BSC нужны `TRON_USDT_CONTRACT`/`BSC_USDT_CONTRACT` + тестовые токены. Mainnet требует явного opt-in через env — случайно не включится.

### Окружение

- **Vite не подхватывает изменения .env на лету** — после правки [client/.env](../client/.env) обязателен полный рестарт dev-сервера.
- **Запуск из сети**: пользователь смотрит проект не только с localhost, но и с публичного IP (текущий: `69.164.242.115`). **С 2026-05-18 BASE_URL клиента определяется динамически** из `window.location.hostname + ':3001'` в [client/src/config/api.ts](../client/src/config/api.ts) — клиент сам подстраивается под хост, через который открыт. DevTools mobile на `localhost:5173` → `localhost:3001` (WebSocket-upgrade проходит, нет polling-fallback'а), телефон в LAN на `public-IP:5173` → `public-IP:3001`. `VITE_API_URL` в [client/.env](../client/.env) остался как **override для production** (когда client и server на разных хостах) — в браузере dev игнорируется.
- **Сервер слушает `0.0.0.0:3001`**, в dev CORS открыт (`origin: '*'`). Доступен снаружи, если порт 3001 не зарезан файрволом хостинга.
- **`nodemon.json` в server/** ограничивает watch только `src/`. Записи в `server/data/*.json` (persistChips, saveRoomsSnapshot) больше не вызывают рестарт. Без этого dev-режим сам себе создавал крэш-цикл: каждая посадка → запись в users.json → рестарт → стек в памяти теряется → клиент видит «бай-ин списан, места нет».
- **Запуск dev**: `npm run dev` из корня поднимает оба процесса через `concurrently`. Логи обоих идут в один stdout с префиксами `[0]` (клиент) и `[1]` (сервер).
- **Освободить занятые dev-порты (3001/5173) на Windows**:
  ```powershell
  $ports=@(3001,5173,5174); foreach($p in $ports){ Get-NetTCPConnection -LocalPort $p -State Listen -EA SilentlyContinue | %{ Stop-Process -Id $_.OwningProcess -Force } }
  ```
  Часто нужно после непрерывных рестартов — старые `node.exe`/`nodemon` зависают.

### Сокеты и game flow

- **Сокеты на клиенте**: единая точка подключения — [client/src/lib/socket.ts](../client/src/lib/socket.ts). `getSocket()` создаёт singleton с JWT из localStorage. Для logout сделан `disconnectSocket()` (вызывается из [authStore.ts](../client/src/store/authStore.ts)).
- **Создатель комнаты входит автоматически**: в хендлере `createRoom` ([server/src/index.ts](../server/src/index.ts)) после успешного `gameManager.createRoom` сразу же `socket.join` + `addPlayer`. Не отправлять `joinRoom` от клиента после `roomCreated` — будет двойной заход.
- **Initial state на mount комнаты**: `GameRoom` при mount шлёт `requestGameState`, сервер отвечает `gameUpdate` + `startCountdown`. Это лекарство от race condition, когда клиент успевает подписаться на события уже **после** того, как сервер сделал broadcast.
- **Реконнект через `requestGameState`**: при mount GameRoom клиент шлёт `requestGameState`. Если юзер числится в `room.players` (например, после refresh), серверный handler вызывает `socket.join(roomId) + addPlayer` (реконнект-ветка) — обновляет `socketId` внутри `Player`. Без этого новый сокет не получал бы `broadcastGameState`, а UI показывал бы пустой стол.
- **Single-session per user**: в `io.use()` middleware — при handshake любые старые сокеты того же `user.id` получают `forceDisconnect` и `disconnect(true)`. Глобальная подписка в [Layout.tsx](../client/src/components/layout/Layout.tsx) показывает toast и редиректит в `/lobby`. **Защита от race condition при refresh:** в `socket.on('disconnect')` handler отложен на 1 сек и проверяет, появился ли уже другой активный сокет того же `user.id` (это типичный случай F5/refresh — старый дисконнектится, новый сразу подключается). Если есть — `handleDisconnect` пропускается, и игрок остаётся в комнате. Без этой защиты при refresh игрок удалялся из waiting-комнаты, повторный вход списывал buy-in заново → дублирование/потеря банкролла.

### Игровой движок

- **Автостарт раздачи**: в `GameManager.scheduleAutoStart(roomId)` — таймер на `settings.autostartDelayMs` (дефолт 10 сек, настраивается админом). Запускается, когда `status='waiting'` и `players.size >= AUTO_START_MIN_PLAYERS` (константа = 2, не настраивается per-table). Вызывается из `addPlayer`, `removePlayer`, `cleanupHand`. Шлёт клиентам `START_COUNTDOWN { endsAt }`.
- **Шоудаун с задержкой**: `endGame` показывает финальное состояние (открытые карты + `GAME_WINNER { winners, handName, winningCards }`) и через `setTimeout(5000)` вызывает `cleanupHand`. `handName` — русское название комбинации, `winningCards` — 5 карт лучшей руки победителя (для подсветки на клиенте).
- **Таймер хода (auto-fold)**: в `emitCurrentTurn` стартует `setTimeout(room.turnDurationMs)` — per-table значение, задаётся при создании стола чипсами `[13, 15, 18, 20, 25]` сек в `CreateRoomModal`. Дефолт глобальный `settings.turnDurationMs` (30 сек) используется как fallback для legacy-снапшотов и старых клиентов. По истечении — `handlePlayerAction('fold')`. `room.turnEndsAt` идёт в `GameState`, клиент рисует обратный отсчёт у PlayerSeat. Сбрасывается в `handlePlayerAction`, `advancePhase`, `endGame`, `cleanupHand`.
- **Таймбанк (двухфазный turn-timer)**: после истечения основного `turnDurationMs` сервер не сразу авто-фолдит, а если у игрока есть `player.timebank > 0` — стартует второй таймер (Phase 2) на `player.timebank` секунд (`Room.timebankTimer` + `room.turnTimebankEndsAt`). По истечении — `auto-fold`. При действии игрока в Phase 2 — списываем elapsed из `player.timebank` (Phase 1 не списывает). Пополнение в `cleanupHand`: каждые `bonusEveryHands` рук за столом — `+bonusSec`, до `capSec`. Стартовый запас даётся в `addPlayer` для нового игрока (`isFolded`/late-entry — без разницы); реконнект сохраняет timebank в памяти. Глобал в [settings.json](../server/data/settings.json) `timebank: { enabled, startSec, bonusSec, bonusEveryHands, capSec, allowPerTableOverride }`. Если `allowPerTableOverride=true` — `CreateRoomModal` показывает секцию (через публичный `GET /api/timebank-config`), создатель стола может задать свой конфиг (без `allowPerTableOverride` поля). Иначе сервер игнорирует присланный `timebank` и копирует глобал.
- **Банкролл и бай-ин**: глобальный банкролл хранится в `users.json:chips`, стек на столе живёт отдельно в `Player.chips` (в памяти). При посадке (`addPlayer`) с банкролла **списывается** запрошенный `buyInAmount`. При выходе (`removePlayer`, `adminForceCloseRoom`, `autoLeaveBrokePlayers`) текущий `player.chips` **возвращается** к банкроллу. `cleanupHand` ничего больше не синкит — стек продолжает жить в памяти. Бай-ин per-table настраивается полями `buyInMinBb`/`buyInMaxBb` (5..1000 BB), дефолт 20-100 BB. На клиенте `BuyInModal` со slider'ом в диапазоне `[bigBlind*minBb, min(bigBlind*maxBb, bankroll)]`. Trade-off: при крэше сервера стек на столе теряется.
- **Late entry**: в playing-комнату можно сесть с обычным buy-in. `canJoinRoom` не блокирует `'in-game'`, `addPlayer` помечает нового игрока `isFolded=true` на текущую раздачу. В `cleanupHand` все `isFolded` сбрасываются — следующая раздача `startGame` раздаст ему карты вместе со всеми.
- **Min-raise валидация** в `handlePlayerAction` (для всех игроков, не только ботов): [bettingRules.ts](../server/src/game/bettingRules.ts) `minRaiseTo(currentBet, lastRaiseSize) = currentBet + lastRaiseSize` (POKER_RULES §5.1) — `lastRaiseSize` трекается в `Room`, инициализируется BB на каждой улице, обновляется при полном raise/bet. Исключение: all-in c остатком меньше min-raise разрешён (incomplete raise, §5.2). Раньше здесь была неверная формула `max(currentBet*2, currentBet+bigBlind)` (баг A1, ломался на 3-bet+) — исправлено 2026-06-15, см. [ROADMAP §B](ROADMAP.md).

### Безопасность

- **Карты соперников НЕ отдаются клиенту до showdown** (фикс утечки 2026-05-17): `getGameState(roomId, viewerId?, withPeek?, showOpponentHud?)` персонализирован. `cards` приходят только владельцу, всем на `showdown`, и админу с включённым peek. `broadcastGameState` итерируется по сокетам комнаты (`io.sockets.adapter.rooms`) и для каждого формирует свой state. **Не пытайся снова отдавать карты всем «для простоты»** — был баг, что любой игрок видел чужие карты через DevTools.
- **HUD соперников — тот же гейт, тот же класс утечки** (§10.21.13, 2026-09-07): при `paidFeatures.hudMode === 'paid'` `hudStats` соперника не уходит зрителю без подписки — параметр `showOpponentHud` у `serializeGameState` по умолчанию `false` (fail-closed), разрешение считает `broadcastGameState` (бесплатный режим / активная подписка / роль `admin` из JWT). Прятать цифры на клиенте бесполезно — их видно в DevTools, ровно как было с картами.
- **Атомарная запись JSON**: `writeJSON` в [storage.ts](../server/src/auth/storage.ts) пишет в `.tmp.<pid>.<ts>` + `renameSync`. Защищает от частично записанного файла при крэше.
- **Admin-peek («глаз админа»)**: кнопка `Eye/EyeOff` в верхнем баре GameRoom — видна только если `useAuthStore.isAdmin`. Toggle шлёт `adminPeekToggle { enabled, roomId }`; сервер проверяет `user.role === 'admin'` и кладёт `user.id` в `GameManager.adminPeekUsers: Set<string>`. Ключ — userId, не socketId: peek переживает переподключение сокета (иначе сворачивание Telegram Mini App пересоздавало сокет и молча гасило peek — фикс 2026-08-27). На клиенте `peekOn` дублируется в `localStorage` ([adminPeek.ts](../client/src/config/adminPeek.ts)), чтобы кнопка-тумблер тоже не сбрасывалась при пересоздании React-дерева.

### Боты

- **Боты («режим онлайна»)**: автоматическое создание 3 столов с ботами (микро 1/2 / низкие 5/10 / средние 25/50). Бот = сущность в `server/data/bots.json` (`id: 'bot:xxx'` префикс, отдельно от users.json). У бота нет socket — `getUserChips`/`persistChips`/`notifyBankroll`/`broadcastGameState` имеют ветки `isBot(id)` (без сетевых вызовов). Бот ходит через [BotManager.scheduleBotDecision](../server/src/game/BotManager.ts) → `botBrain.decideAction` → `handlePlayerAction` (тот же путь, что у человека). Включается через `settings.botMode.enabled`. Per-bot цель PnL (`zero`/`plus`/`minus`) меняется в админ-вкладке «Боты». peekMode (`river`/`turn`/`full`) — глобально в Settings. **Бот-столы выглядят как обычные** в `getRoomList` (флаг `isBotTable` отдаётся ТОЛЬКО в `getAdminRoomList`).
- **Анти-фрод бота** ([botBrain.ts](../server/src/game/botBrain.ts)): persona per-bot (`aggression`/`bluffRate`/`heroFoldRate`/`slowplayRate`/`vpip`), seeded RNG per `(botId + handIndex)`, bi-modal reaction time, hero-fold/slowplay/bluff/mistake-injection инъекции, bluff-catch quota, riskShift в зависимости от drift PnL. **PnL-балансировка не бинарная** — через сдвиг порогов fold/call/raise.
- **botBrain anti-escalation** (2026-05-18): (1) pot odds check — force fold если `effective < toCall/(pot+toCall) - 0.05`; (2) SPR awareness — если `(myChips - toCall) / (pot + toCall) < 2` и phase!=preflop: либо all-in (effective>0.80 или peek-win), либо fold (effective<0.62); (3) ужесточённые preflop thresholds — fold 0.30→0.35, call 0.55→0.62, raise 0.78→0.85; (4) cap raise size — preflop max `max(currentBet*3, bigBlind*4)` без monster, postflop max `currentBet + pot` без monster.
- **BotManager refill API**: `setBotChips(botId, chips)` и `refillAllBankrolls(chips)` сбрасывают `runtime.realizedPnL`/`handsPlayed`/`handStartChips`. Admin endpoints: `POST /api/admin/bots/refill { chips }`, `PATCH /api/admin/bots/:id { chips }`.

- **Auth-страницы Login/Register**: единый фон `/images/front-reg.png` + `bg-black/50` overlay. Корневой контейнер — `relative min-h-[calc(100dvh-4rem)] overflow-hidden`. `4rem` вычитает navbar.
- **Bankroll-индикатор в navbar**: [Layout.tsx](../client/src/components/layout/Layout.tsx) при mount делает `fetch /api/auth/me` и подписывается на socket-event `bankrollUpdate { chips }`. Сервер шлёт через `GameManager.notifyBankroll(userId, chips?)` после каждого `persistChips`.
- **Lobby шапка и табы форматов**: `formatTab: 'all' | 'nlh' | 'shortdeck'` в [useRoomFilters.ts](../client/src/hooks/useRoomFilters.ts) — работают все три (Шорт-дэк реализован с 2026-06-13). Счётчики (`onlineCount`, `tableCount`) считаются на клиенте по `rooms[]`.

### Прочее

- **Глобальные настройки**: [server/data/settings.json](../server/data/settings.json) — `turnDurationMs`, `autostartDelayMs`, `defaultPlayerChips` плюс вложенные блоки `timebank`, `botMode`, `paidFeatures` (Rabbit Hunting + `hudMode`), `payments` (крипто-депозиты/выплаты), `responsibleGambling`. Загружается в `GameManager.loadSettings()` с глубоким merge (вложенные блоки мержатся по полям — частичный патч не затирает остальное). Меняется через `PUT /api/admin/settings`, валидация — [settingsValidation.ts](../server/src/routes/settingsValidation.ts).
- **Админ может менять собственные `chips`**: серверный `PATCH /api/admin/users/:id` блокирует только self-change для `role`/`banned`. Чипсы себе — можно.
- **Mapping `joinDenied` reason → message**: на клиенте в [GameRoom.tsx](../client/src/pages/GameRoom.tsx) и [Lobby.tsx](../client/src/pages/Lobby.tsx) технические reason'ы (`no-chips`, `kicked`, `closed`, `in-game`) маппятся на русские сообщения для toast.
- **getFutureBoardCards в deck.ts** учитывает burn-карты. `dealCommunityCards` использует `pop()` (берёт с конца массива) и сжигает 1 карту перед каждым флопом/тёрном/ривером. Поэтому `room.deck.slice(0, 5)` показывал бы карты с **дна** колоды. Правильно: `getFutureBoardCards(deck, alreadyOnBoardCount)` — возвращает реальные будущие community-карты, скипая burn'ы. Используется в admin-peek и в bot-логике.

## Грабли — на что наступали (исторические)

- **`toBeInTheDocument()` даёт ложный провал на модалке-портале** (найдено 2026-09-09 на тесте кнопки «i» у карточки турнира): `findByText` УЖЕ нашёл узел, а матчер всё равно падает с «element could not be found in the document» — портал предыдущего теста остаётся отсоединённым от `document`, и проверка вхождения срабатывает не на том дереве. Симптом обманчивый: кажется, что элемент не отрисовался, хотя `document.body.textContent` его содержит. Лечение: проверять сам найденный узел (`expect(el.textContent).toBe(...)`), а не его вхождение в документ. Касается всех модалок на `createPortal` — их в проекте много (TournamentInfoModal, TournamentDetailsModal, CreateTournamentModal).

- **`npm install <pkg>` в client/ может обнулить транзитивные deps**: если в `package.json` объявлены не все используемые пакеты (только часть тянулась транзитивно), то `npm install <new-pkg>` перестроит `node_modules` строго по `package.json` — и недекларированные пропадут. Лечение: явно объявить ВСЕ используемые import'ы в `dependencies`. Это случилось при установке `socket.io-client` — пропали `react-router-dom`, `zustand`, `framer-motion`, `lucide-react`, `@tailwindcss/vite`.
- **Порт 3001 регулярно занят** старым `node.exe` от предыдущего запуска `dev:server` — даже после Ctrl+C nodemon. Перед рестартом стоит освобождать порты (см. сниппет выше).
- **Подписка на сокет ПОСЛЕ навигации = пропуск событий**: socket.io не буферит события без активных подписчиков. Если сервер делает `broadcastGameState` сразу после `addPlayer`, а клиент в этот момент ещё на Lobby (без подписки на `gameUpdate`) и только потом переходит на `/game/:roomId` — события теряются. Лечение — клиент шлёт `requestGameState` на mount, сервер отвечает текущим состоянием.
- **Создание комнаты не означало «вход в комнату»**: первая версия `createRoom` хендлера только генерировала id — `socket.join` и `addPlayer` не делались. Клиент навигировал на `/game/:roomId`, но пользователя в `room.players` не было, поэтому автостарт не срабатывал. Лечение в [server/src/index.ts](../server/src/index.ts) — после успеха `createRoom` сразу `socket.join` + `addPlayer`.
- **Showdown без активных игроков крашил сервер**: если все active-по-`isFolded` имели `chips=0` или были disconnected, `nextPlayer` доходил до `showdown`, а `determineWinner` падал. Лечение — guard в [hands.ts](../server/src/game/hands.ts) на пустой `activePlayers` и в `showdown` на пустой `winners`.
- **Cross-directory импорт shared в server через tsx+NodeNext не работает**: пробовал убрать дубли типов через `paths: { "@shared": ["../shared/index.ts"] }` и через relative `import from '../../../shared/index.js'`. Tsx loader не подхватывает `.ts` файл вне `server/src/` при ESM-импорте с `.js` extension — Node ошибается `SyntaxError: does not provide an export named 'SOCKET_EVENTS'`. Откатил, оставил дубли. Реальное решение — npm workspaces или предкомпиляция shared в `.js`, но это перестройка проекта.
- **AnimatePresence ломал mount дочерних motion** (закрыто 2026-05-21): `<AnimatePresence mode="wait">` в Layout вокруг children останавливал initial-анимации множества motion-компонентов внутри GameRoom. DBG-overlay был виден, но `PlayerSeat`/`Card` оставались в initial с `opacity:0`. F5 чинил (cold mount без exit-transition). Лечение: убрал AnimatePresence из Layout. Не возвращать.
- **nodemon на data/ создаёт crash-loop**: если nodemon следит за всем `server/`, любая запись в `server/data/*.json` (persistChips, saveRoomsSnapshot) триггерит рестарт. Активная раздача (deck/pot) теряется. Клиент видит «бай-ин списан, места нет». Лечение: `nodemon.json` watch только `src/`. Не «оптимизировать» обратно.
- **Stop-Process node -Force в момент write** может побить JSON-файл — `bots.json` стал пустыми пробелами при serial убийстве node в момент `writeJSON`. Сейчас защищено seedDefaultPool при пустом пуле — если файл побился полностью, пересоздаст 12 ботов. Но не панацея.
- **`em`-размер двузначного ранга («10») на цветной колоде вылезал за края карты** (закрыто 2026-06-21): крупный номинал в [Card.tsx](../client/src/components/game/Card.tsx) (deck='colored') задан как `text-[2.24em]` — em считается от текущего `font-size` карты (`SIZE_CLASS`: `sm`/`md`/`lg`), а ширина/font-size у этих трёх размеров НЕ пропорциональны (`sm` даёт самое тесное соотношение). Однозначные ранги влезали, двузначный «10» — нет, особенно на `sm`/`md` (карты в руке/на борде за столом; в `/deck-preview` все карты `lg`, там было незаметно). Первая попытка — уменьшить `em` для двузначных рангов — убрала переполнение, но сделала «10» визуально мельче соседних номиналов. Финальное лечение: `scale-x-75` + `origin-right` на span с тем же `text-[2.24em]` — высота/насыщенность цифры та же, сжата только ширина.
- **`resolveShowdown`'s `pot`-параметр НЕ контролирует размер выплаты** (найдено 2026-06-26, при реализации Double Board/RIMT): выплата считается от `totalCommitted` каждого игрока (его вклада в банк), а аргумент `pot` влияет ТОЛЬКО на пропорциональный рейк/бэдбит-математику. Изначальный план для `resolveMultiRunShowdown` ([multiRunService.ts](../server/src/game/multiRunService.ts)) предполагал вызывать `resolveShowdown` с ПОЛОВИНОЙ банка на каждый из 2 бордов и СУММИРОВАТЬ результаты — это удвоило бы реальную выплату (банк брался бы из `totalCommitted` целиком на каждом вызове). Лечение: вызывать `resolveShowdown` на каждом борде с ПОЛНЫМ исходным `pot` (как если бы этот борд один решал раздачу), затем УСРЕДНЯТЬ (не суммировать) результаты по числу прогонов, с детерминированной коррекцией остатка первому победителю — для сохранения целостности банка. Проверено `multiRunService.test.ts` (chip conservation) + живым прогоном полного тестового набора.
- **Невалидное действие в `handlePlayerAction` тушило safety-net таймер и вешало стол навсегда** (закрыто 2026-07-03, найдено по жалобе «стол завис» — 3 бот-стола висели в preflop до 29 часов, `watchdog` их не видел т.к. игнорит `isBotTable`): `clearTurnTimers(room)` вызывался СРАЗУ после проверки «это его ход», а валидация конкретного действия (locked caller re-raise §5.2, невалидный check, нелегальный raise) шла ПОСЛЕ — при её провале был тихий `return` без `nextPlayer()`. Таймер уже потушен → стол замирал без единой ошибки в логах. Триггерилось ботом: `botBrain.ts` не знал про `room.lockedCallers` и мог выбрать `raise`, будучи запертым incomplete all-in'ом. Лечение: вся валидация в [GameManager.ts](../server/src/game/GameManager.ts) `handlePlayerAction` перенесена ПЕРЕД `clearTurnTimers`; дополнительно `botBrain.decideAction` теперь получает `ctx.isLockedCaller` (из `buildBotContext`) и сам понижает `raise` до `call`, чтобы не терять ход. Тесты: `GameManager.allInReopen.test.ts` (таймер переживает невалидную попытку и сам фолдит по таймауту), `botBrain.test.ts` (`isLockedCaller` → `raise` понижается до `call`).
- **`levelUpMinutes` турнира был мёртвым полем** (закрыто 2026-07-03, найдено при подготовке тестового MTT — просили рост блайндов «каждые 5 минут»): `buildBlindSchedule` брал длительность уровня только из `SPEED_DURATIONS[blindSpeed]` (slow/regular/turbo/hyper = 20/12/6/3 мин), `levelUpMinutes` валидировался и сохранялся в `TournamentInfo`, но нигде не читался — реальная длительность уровня всегда была одной из 4 фиксированных, точных «5 минут» получить было нельзя. Лечение: [tournamentSchedule.ts](../server/src/game/tournament/tournamentSchedule.ts) `buildBlindSchedule(startingStack, levelUpMinutes)` — `durationMin` теперь напрямую из аргумента; оба вызова в [TournamentManager.ts](../server/src/game/tournament/TournamentManager.ts) (`create`, `restoreTournaments`) передают `levelUpMinutes` вместо `blindSpeed`. `blindSpeed` в схеме теперь чисто косметическое поле (UI-лейбл «Скорость блайндов»), на расписание не влияет.
- **MTT: турнирные столы наследовали cash-логику дисконнекта/посадки без поправки на турнирные инварианты** (закрыто 2026-06-23, найдено живым прогоном в браузере, не unit-тестами): (1) `handleDisconnect` для `status==='waiting'` всегда звал `removePlayer`, который на турнирном столе = форфейт (§0.2-A, защита от фритролла). Для неровного MTT-сплита (стол с 1 игроком, ждёт второго) это форфейтило игрока за дисконнект ДО начала раздачи — его вины тут нет. Лечение: `room.tournamentId` исключён из этой ветки, держим место сит-аутом, как в `playing`. (2) Поздняя регистрация (`TournamentManager.register`) сажала игрока через `seatTournamentPlayer`, но не звала `startGame` — если игрок заполнял именно тот неровный стол с 1 игроком, раздача никогда не стартовала (стол навечно в `waiting`/«Ждём второго игрока»). `startGame` безопасно no-op на уже играющих/неполных столах — добавлен явный вызов после посадки. Оба бага не ловились тестами, потому что `TournamentManager.*.test.ts` эмулируют форфейт напрямую через `gm.removePlayer(...)`, а не через реальный `handleDisconnect`/`register`-путь — живой прогон в браузере (2 реальные сессии через `gstack browse`) их и нашёл. Тесты на оба случая: `GameManager.tournamentMove.test.ts` (сит-аут вместо форфейта), `TournamentManager.mtt.test.ts` (late-reg реально стартует раздачу).
- **`BLIND_LADDER` — конечный жёстко заданный список, а не формула** (найдено 2026-07-03, живым прогоном: турнир со стартстеком 750000 «завис» на 10000/20000 без роста на 3.5+ часа): `buildBlindSchedule` берёт срез готового массива из 22 уровней начиная с ближайшего к `startingStack/75`; при большом стеке старт попадает почти в конец массива и уровней остаётся мало, а `currentLevelForElapsed` намеренно держит последний уровень навсегда (чтобы не остаться совсем без блайндов). Из-за этого при большом стеке или очень долгом турнире рост блайндов останавливается — без давления на банкроллы игра может идти бесконечно. Лечение — не расширение лестницы, а анте (растёт вместе с блайндами, `round(bigBlind/8)`), которое продолжает вымывать фишки из игры даже когда блайнды упёрлись в потолок, см. §10.19 в [ROADMAP.md](ROADMAP.md).
- **Тесты турнирных сценариев с несколькими столами не должны предполагать `tableIds[0]` — рассадка случайна** (найдено 2026-07-03, флаки-тест обнаружился только при повторных прогонах): `startMtt` перемешивает entries (Fisher-Yates) перед распределением по столам — при 3 игроках/`tableSize=2` конкретный игрок с вероятностью ~1/3 попадает на «второй» стол, а не на первый. Тест `TournamentManager.mtt.test.ts` («принудительная отмена…») жёстко брал `started.tableIds[0]` и вызывал `gm.removePlayer(tableId, 'A')` — если A оказывался на другом столе, форфейт не срабатывал (`room.players.has('A')` false), `entry.status` не менялся на `eliminated`, тест падал недетерминированно. Лечение: брать РЕАЛЬНЫЙ стол игрока через `entries.find(e => e.userId === 'A').tableId`, не индекс массива.
- **Завершение турнира закрывало стол молча — игрок узнавал об этом только через ошибку** (закрыто 2026-07-03, найдено живым прогоном: собственный аккаунт выиграл тестовый MTT, стол «завис», затем `JOIN_DENIED{reason:'not-found'}` и редирект в лобби): `TournamentManager.finish()`/`handleBust()` вызывали `closeTournamentTable`/удаляли игрока из `room.players` БЕЗ единого сокет-события — приз при этом начислялся корректно, но клиент не получал никакого сигнала о завершении, кроме следующего `requestGameState` на уже несуществующую комнату. Лечение: новое событие `SOCKET_EVENTS.TOURNAMENT_RESULT` + `GameManager.notifyTournamentResult(userId, payload)` (таргетный emit по сокету игрока, ДО закрытия стола/удаления из room.players) — вызывается и при бaсте (место + оценка приза), и при финише (победитель + финальный приз). Клиент слушает событие глобально в `Layout.tsx` (не только на странице стола — игрок может быть где угодно), показывает модалку результата, при закрытии переходит на `/tournaments`.
- **`Date.now()` напрямую в теле React-компонента — линт-ошибка `react-hooks/purity`** (найдено 2026-07-07, при добавлении `regNotOpenYet` в `TournamentCard.tsx`): `eslint-plugin-react-hooks` ловит прямой вызов impure-функции (`Date.now`/`Math.random` и т.п.) прямо в теле компонента как потенциально нестабильный рендер, но НЕ ловит его внутри отдельно объявленной обычной функции-хелпера (статический анализ не трассирует через границу функции) — см. уже существующий `isLateRegOpen(t)` в том же файле, который прошёл линт без вопросов. Лечение: любое сравнение с `Date.now()` в компоненте выносить в top-level функцию-хелпер (принимает нужные поля, возвращает bool/значение), не инлайнить в тело компонента.
- **Модалка внутри страницы с `relative z-N` — «запирается» в её stacking context, нижний таб-бар перекрывает её независимо от собственного z-index** (найдено 2026-07-07, живым тестом в браузере: подсказки в `CreateTournamentModal` уходили под нижнее меню Главная/Лобби/Турниры): `Tournaments.tsx` оборачивает контент в `<div className="... relative z-10">`; `position:relative` + явный `z-index` создаёт НОВЫЙ stacking context — любой fixed-элемент внутри (даже с `z-[9999]`) снаружи виден как единый блок на уровне «10», и нижний таб-бар (`z-40`, `Layout.tsx`) рисуется поверх целиком. Диагностика через JS в консоли браузера (`getComputedStyle` + обход `parentElement` до body) — надёжнее, чем рассуждать о CSS-спеке на бумаге. Лечение: модалку рендерить через `createPortal(..., document.body)` — выходит из ЛЮБОГО stacking context страницы-хоста. Починено в `CreateTournamentModal.tsx` и `CreateRoomModal.tsx`. Важно: у `Lobby.tsx` (classic, legacy fallback) та же обёртка `relative z-10` реально накрывает модалку в JSX (баг подтверждён разбором вложенности), а у `LobbyRedesign.tsx` (текущий дефолт) — нет, там `CreateRoomModal` рендерится уже ПОСЛЕ закрытия этой обёртки (совпадение структуры, не осознанная защита). При добавлении НОВОЙ модалки — либо портал сразу, либо проверять, что она не закрывается в JSX анализе).
- **`BotManager.disableMode()` закрывал авто-столы только по карте УЖЕ ПОДСЕВШИХ ботов, а не по карте СОЗДАННЫХ столов** (закрыто 2026-07-07, найдено живым тестом: `PUT /api/admin/settings {botMode:{enabled:false}}` сразу после рестарта сервера — 3 авто-стола остались висеть): боты подсаживаются волнами со сдвигом (`createTableWithBots` — часть сразу, часть через `setTimeout` минутами позже, см. `сразу=N, придут позже=M` в логе). `disableMode()` закрывал столы через `for (const roomId of new Set(this.botTable.values()))` — `botTable` это карта botId→roomId ТОЛЬКО подсевших ботов; `botTableLevels` (roomId→level, регистрируется в момент СОЗДАНИЯ стола, до посадки хоть одного бота) не использовался вообще. Если disable вызван до первой посадки (типично сразу после рестарта) — `botTable` пуст, столы не закрываются, хотя лог пишет «Bot mode DISABLED». Лечение: закрывать по объединению `botTableLevels.keys() ∪ botTable.values()`. Тест (`BotManager.disableMode.test.ts`) не может воспроизвести через реальную посадку — `autoRefillForBuyIn` перед выбором кандидатов ВСЕГДА докидывает ботам фишки под любой заданный buyIn (даже 999_999_999), так что «недостаточно фишек» не помогает получить 0 подсевших; пришлось напрямую зарегистрировать roomId в приватной `botTableLevels` (`as unknown as {...}`), воспроизводя точный момент «стол создан, но ещё никто не подсел».

- **Socket-обработчик без проверки `data` на существование = DoS всего сервера одним событием** (закрыто 2026-08-23, найдено ручным white-box security review при подготовке Strix-пентеста): TS-тип аргумента (`data: { roomId: string }`) — компайл-тайм; рантайм socket.io ничего не валидирует, `data` может прийти `undefined` (клиент шлёт `socket.emit('playerAction')` без второго аргумента — намеренно или багом). Большинство обработчиков в [registerSocketHandlers.ts](../server/src/socket/registerSocketHandlers.ts) (`CREATE_ROOM`/`LEAVE_ROOM`/`REQUEST_GAME_STATE`/`OBSERVE_ROOM`/`JOIN_ROOM`/`JOIN_WAITLIST`/`LEAVE_WAITLIST`/`PLAYER_ACTION`/`START_GAME`) читали `data.roomId`/`data.action` без проверки → `TypeError`. Проверено изолированным репро на реальном `socket.io@4.8.3` (отдельный порт, без связи с проектным сервером): исключение из `socket.on()`-колбэка НЕ гасится библиотекой, долетает до process-level `uncaughtException`; в `index.ts` глобального хендлера нет → Node убивает весь процесс, а `nodemon.json` не рестартует сам по себе (только по изменению файла) — сервер лежит для всех столов до ручного вмешательства. Любой залогиненный игрок (регистрация open/бесплатная) мог этим положить весь рум одной строкой в консоли браузера. Лечение: `if (!data || typeof data.roomId !== 'string') return;` в начале каждого такого обработчика (паттерн уже был у `SET_AUTO_TOPUP`/`SET_HAND_HINT`/`ADMIN_PEEK_TOGGLE`/`SEND_EMOJI` — не был последователен). Заодно закрыт смежный баг: `PLAYER_ACTION`'s `amount` тоже не проверялся рантаймом — нечисловое значение (строка) присваивалось в `room.currentBet` как есть, и `minRaiseTo` (`currentBet + lastRaiseSize`) при следующем raise превращалось в конкатенацию строк вместо сложения (минимальный рейз улетал в абсурдные значения, блокируя легальные рейзы на раздаче). Правило на будущее: **любой новый socket-обработчик обязан начинаться с runtime-guard на `data`** — TS-тип входного payload'а защиты не даёт. Тест: [registerSocketHandlers.security.test.ts](../server/src/socket/__tests__/registerSocketHandlers.security.test.ts) (20 тестов, включая mutation-проверку — временный откат guard'а подтвердил, что тест ловит регрессию тем же `TypeError`, что и живое репро).
- **`<main>` в Layout.tsx слушает `touchstart`/`touchend` для свайпа между вкладками нижнего бара — любой дочерний горизонтальный драг/карусель должен `stopPropagation()` на этих же событиях, иначе оба обработчика ловят один и тот же палец** (закрыто 2026-08-30, найдено живым тестом на реальном телефоне в Telegram: карусель кэш-столов на главной при свайпе сама скроллилась ПРАВИЛЬНО, но пользователя параллельно кидало по вкладкам `tabRoutes` — Главная→Лобби→Клуб→Админ). Причина: `Layout.tsx` вешает `onTouchStart`/`onTouchEnd` (React synthetic touch events) прямо на `<main>`, который оборачивает КАЖДУЮ страницу, и по `dx`/`dy` between них навигирует по фиксированному массиву `tabRoutes`. `MainMenu.tsx`'s карусель обрабатывала жест через Pointer Events (`onPointerDown/Move/Up`) и звала `e.preventDefault()` — это гасит нативный scroll/back-gesture браузера, но НЕ мешает параллельно летящим нативным `touchstart`/`touchend`, которые всё равно всплывают до `<main>` (Pointer Events и Touch Events — разные системы событий, `preventDefault` одной не блокирует другую). Диагностировано занявшим много времени перебором гипотез (CSS `overscroll-behavior`, нативные жесты Telegram/WKWebView) — реальную причину нашли только прогнав exhaustive-поиск по `touchstart`/`touchend` и git-логу. Лечение: на дочернем элементе с собственным горизонтальным жестом — `onTouchStart={(e) => e.stopPropagation()}` + `onTouchEnd={(e) => e.stopPropagation()}` (см. `MainMenu.tsx`). Правило на будущее: **любой новый горизонтальный свайп/драг/карусель на странице с нижним таб-баром обязан стопать propagation на `touchstart`/`touchend`**, иначе будет молча конфликтовать с переключением вкладок.
- **Анти-коллюжен был опциональной галочкой у создателя стола, по умолчанию выключен** (закрыто 2026-08-24, security review): `antiCollusionEnabled` при `CREATE_ROOM` шёл от клиента напрямую без role-проверки (в отличие от соседнего `pinned`, который правильно гейтится `user.role==='admin'`).
